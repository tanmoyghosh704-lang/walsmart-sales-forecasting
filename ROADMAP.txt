================================================================================
PROJECT ROADMAP & RESOURCE BREAKDOWN: WALMART M5 DEMAND FORECASTING MLOPS
================================================================================

PROJECT OVERVIEW:
An end-to-end, production-shaped demand forecasting system built on
Kaggle's M5 Forecasting - Accuracy dataset (Walmart). Benchmarks 7
forecasting approaches (naive seasonal baseline, SVM, SARIMA, Linear
Regression, Random Forest, XGBoost, LightGBM) on 100 high-volume
store-item series over a 28-day held-out horizon, tracks and registers
every model via MLflow with conditional champion auto-promotion,
versions data via DVC/DagsHub, serves forecasts via FastAPI + Docker,
orchestrates retraining via Airflow, monitors the live service via
Prometheus/Grafana (including a prediction-drift check), and provides
an interactive Streamlit comparison UI.

PHASE 1: DATA ACQUISITION & SCOPING
================================================================================

1. DOWNLOAD RAW M5 DATA:
   kaggle competitions download -c m5-forecasting-accuracy -p data/raw
   cd data/raw && unzip m5-forecasting-accuracy.zip && rm *.zip

   Files: sales_train_validation.csv (30,490 series x 1,913 days),
   calendar.csv (date/holiday/SNAP mapping), sell_prices.csv (weekly
   price per store-item), sales_train_evaluation.csv, sample_submission.csv.

2. SCOPE THE DATASET DOWN (src/data_prep.py):
   - Full dataset has ~30,490 store-item series -- too many to iterate on.
   - Select TOP 100 SERIES BY TOTAL HISTORICAL VOLUME, not a random
     sample. High-volume series have proportionally fewer zero-sales
     days, which matters directly for MAPE.
   - This skews the subset toward FOODS (grocery items sell far more
     often than hobbies or household goods) -- a real bias, stated
     explicitly rather than hidden.
   - Reshape wide format (d_1...d_1913 columns) to long format
     (id, date, sales, ...) via pandas.melt.
   - Output: data/processed/subset_long.csv (191,300 rows).

3. NAIVE BASELINE, BEFORE ANY MODELING (src/baseline.py):
   - Seasonal-naive (lag-7): each series' last 7 observed training days,
     tiled across the 28-day test horizon.
   - 28-day held-out test window (matches M5's own competition horizon).
   - Result: 78.58% mean per-series MAPE / 10.75% aggregate MAPE.

PHASE 2: EXPLORATORY DATA ANALYSIS
================================================================================

1. NOTEBOOK: notebooks/eda.ipynb
   - Weekly seasonality: weekend sales (~40 units/day) vs. midweek (~28).
   - SNAP (food-assistance) effect: real, consistent bump on SNAP days in

================================================================================
PHASE 3: PER-SERIES MODELS -- SVM & ARIMA
================================================================================

1. WHY PER-SERIES FOR THESE TWO:
   SVM and ARIMA are both trained on a single series' own history --
   neither has a natural "global across series" form. 100 series = 100
   independent models for each.

2. SVM (src/train_svm.py):
   - Per-series SVR (Support Vector Regression) with an RBF kernel,
     wrapped in a StandardScaler -> SVR pipeline (SVR is scale-sensitive).
   - SVR has no built-in trend/seasonality decomposition, so features
     are engineered explicitly: a linear trend index, a sin/cos
     encoding of day-of-week (cyclical, so Sunday and Monday stay
     close together instead of 6 apart), and SNAP as a regular feature.
   - Result: 60.37% mean per-series MAPE / 7.83% aggregate MAPE.

3. ARIMA / SARIMA (src/train_arima.py):
   - `pmdarima.auto_arima`, seasonal=True, m=7 (weekly seasonality),
     SNAP as an exogenous regressor.
   - PARALLELIZED across CPU cores via joblib (a single auto_arima call
     takes ~35s; 100 sequential would be 1hr+).
   - GOTCHA (nested parallelism): joblib's `n_jobs` only bounds worker
     *process* count, not each process's internal BLAS/OpenMP *thread*
     count. numpy/scipy/statsmodels each try to use every core by
     default regardless of how many sibling processes are already
     running. Fix: set OMP_NUM_THREADS, OPENBLAS_NUM_THREADS,
     MKL_NUM_THREADS, NUMEXPR_NUM_THREADS, VECLIB_MAXIMUM_THREADS = "1"
     before importing numpy/scipy/statsmodels (they read these at
     import time).
   - Result: 85.21% mean / 43.87% median / 18.46% aggregate MAPE --
     worse than the naive baseline on every framing. Traced to one
     series with an 856% single-series MAPE from a real stockout mid
     test-window (see Phase 5, champion selection).

================================================================================
PHASE 4: GLOBAL ML MODELS -- FEATURE ENGINEERING & TRAINING
================================================================================

1. GLOBAL VS. PER-SERIES (key design fork):
   - Per-series (SVM/ARIMA): 100 separate models, each blind to every
     other series.
   - GLOBAL (this phase): ONE model per algorithm, trained on all 100
     series stacked into a single table, with store_id/item_id/dept_id/
     cat_id/state_id as FEATURES. This mirrors how the real M5
     competition's top solutions actually approached it.

2. LEAKAGE-SAFE FEATURE ENGINEERING (src/feature_engineering.py):
   - CONCEPT -- why lag_28, not lag_7: this is a 28-day-AHEAD forecast,
     not 1-day-ahead. A lag_7 feature is invalid for most of the test
     window (predicting day 15 of the horizon with "sales 7 days ago"
     needs sales from day 8 of the horizon, which hasn't happened yet).
     lag_28 is the LARGEST lag that stays valid for the ENTIRE 28-day
     horizon.
   - Features: lag_28, rolling_mean_7_lag28, rolling_mean_28_lag28,
     rolling_std_28_lag28, wday/month/year, is_weekend, has_event, snap,
     sell_price (joined from sell_prices.csv).
   - Categorical encoding: label/integer codes for tree models; ONE-HOT
     for Linear Regression via sklearn ColumnTransformer.
   - Output: data/processed/ml_features.csv (185,800 rows).

3. TRAINING (src/train_ml_models.py):
   - Linear Regression, Random Forest, XGBoost, LightGBM -- one
     `.fit()`/`.predict()` call each (no per-series loop).
   - LightGBM given TRUE categorical columns for better split quality
     than raw integer codes.
   - No hyperparameter tuning -- sensible defaults only.
   - Results (aggregate MAPE): LightGBM 5.82%, Linear Regression 6.45%,
     XGBoost 6.48%, Random Forest 7.29%.

PHASE 5: EXPERIMENT TRACKING, MODEL REGISTRY & DATA VERSIONING
================================================================================

1. MLFLOW TRACKING SERVER (not a raw sqlite:/// path):
   mlflow server --backend-store-uri sqlite:///mlflow.db --host 0.0.0.0 \
     --allowed-hosts "host.docker.internal:5000,127.0.0.1:5000,localhost:5000"

   - CONCEPT -- why a server, not a bare local file store: MLflow's local
     file-based artifact store bakes an ABSOLUTE HOST FILESYSTEM PATH
     into each experiment's artifact location at creation time, which
     breaks the moment a client (e.g. a Docker container) runs anywhere
     else. Routing through a tracking server means clients talk to a
     network address, and the server resolves storage on its own
     filesystem.
   - `--allowed-hosts` needed because MLflow 3.x has built-in DNS-
     rebinding protection that 403s requests whose Host header isn't on
     an allowlist.

2. LOGGING PATTERN:
   - Per-series models (SVM, ARIMA): one PARENT run per training job
     + one NESTED run per series, registering each under its own name
     (`svm_<series_id>`, `arima_<series_id>`).
   - Global models: one run each, registered as `sales_<model_name>`.

3. DATA VERSIONING (DVC + DagsHub):
   dvc remote add origin https://dagshub.com/<user>/<repo>.dvc
   dvc remote modify origin --local auth basic
   dvc remote modify origin --local user <username>
   dvc remote modify origin --local password <token>
   dvc add data/raw data/processed
   dvc push -r origin

   - Credentials go in `.dvc/config.local` (gitignored), never the
     committed `.dvc/config`.
   - `dvc push` only pushes DATA, not git history. A separate
     `git push dagshub master` is needed for the DagsHub Files tab to
     show actual code.

4. CHAMPION SELECTION & CONDITIONAL AUTO-PROMOTION:
   - src/compare_models.py: assembles every model's summary + per-series
     MAPE files into one table, sorted by AGGREGATE MAPE.
   - CONCEPT -- why aggregate MAPE, not mean per-series MAPE, as the
     SELECTION metric: ARIMA's mean per-series MAPE (85%) was dragged
     above even the naive baseline by ONE series with an 856% error --
     a genuine stockout mid-test-window, invisible in training history.
     Aggregate MAPE is far less sensitive to a single pathological
     series, which is the property wanted in a selection metric.
   - src/promote_champion.py: re-points the MLflow registry's `champion`
     ALIAS to whichever model has the best aggregate MAPE, but ONLY if
     it beats the CURRENT champion's aggregate MAPE (looked up via the
     run that produced it, not a cached number).
   - Restricted to the 4 GLOBAL models only: each has exactly one
     registered name, so one alias can mean "the current best version
     of this name." SVM/ARIMA are per-series (100 separately-registered
     names each) -- no single name an alias could represent.
   - Winner: LightGBM, 5.82% aggregate MAPE (45.8% relative improvement
     over the naive baseline). Registered as `sales_lightgbm@champion`.

PHASE 6: SERVING -- FASTAPI + DOCKER
================================================================================

1. FASTAPI APP (serving/app.py):
   - GET /health -- liveness + forecast-window info.
   - GET /predict?series_id=...&horizon=... -- loads the requested
     series' SVM model via `mlflow.pyfunc.load_model
     ("models:/svm_<series_id>/latest")`, cached per-process.
   - CONCEPT -- forecast window is bounded, not open-ended: models were
     trained through a fixed date; the `snap` feature they need for
     future dates only has REAL (not fabricated) values as far as
     calendar.csv actually extends.
   - GET /metrics -- Prometheus scrape endpoint (see Phase 8).

2. DOCKERFILE (serving/Dockerfile):
   docker build -f serving/Dockerfile -t m5-forecast-api .
   docker run -p 8000:8000 -e MLFLOW_TRACKING_URI=http://host.docker.internal:5000 \
     m5-forecast-api

   - GOTCHA: do NOT bake mlflow.db/mlruns into the image -- baked-in
     artifact paths break inside a container. Pass
     MLFLOW_TRACKING_URI as an env var instead.

PHASE 7: ORCHESTRATION -- AIRFLOW (DOCKER COMPOSE)
================================================================================

1. WHY DOCKER COMPOSE, NOT NATIVE PIP INSTALL:
   Airflow doesn't officially support running natively on Windows.

2. STACK (docker-compose.yaml): Postgres (Airflow's OWN metadata DB) +
   webserver + scheduler, LocalExecutor.
   docker compose up airflow-init      # one-off: migrate DB, create admin user
   docker compose up -d                # webserver + scheduler

3. TASK DEPENDENCIES INSTALLED IN AN ISOLATED VENV (airflow/Dockerfile):
   - Installing mlflow/scikit-learn/etc. directly into Airflow's own
     Python environment conflicts with versions Airflow's own
     constraints file pins. Fix: `python -m venv /opt/airflow/task_venv`,
     install everything there instead, and invoke that venv's python
     directly from the DAG.
   - Also needed: `apt-get install libgomp1` -- LightGBM's compiled
     extension needs it at import time, and the base Debian image
     doesn't ship it.

4. DAG STRUCTURE (airflow/dags/retrain_dag.py, dag_id=m5_full_retrain):
     retrain_baseline  ---\
     retrain_svm       ----\
     retrain_arima     -----+--> compare_models --> promote_champion
     build_features -> retrain_ml_models --/

   - `max_active_runs=1`: catchup=False still auto-runs the single most
     recent past interval on DAG activation, which can overlap with a
     manual trigger.
   - `execution_timeout` on every task so a hung task fails loudly
     instead of blocking the DAG indefinitely.

5. GOTCHA -- RESOURCE CONSTRAINTS ON SMALL DEV MACHINES:
   Running several memory-heavy tasks concurrently (SVM + ARIMA + 4 ML
   models fitting at once) can exceed what a modest host can sustain.
   Diagnose with `docker stats`, Docker Desktop's settings file, and
   (on Windows/WSL2) `%USERPROFILE%\.wslconfig` for an explicit memory
   override. A structural fix beyond tuning any single task: run heavy
   tasks sequentially instead of in parallel, trading DAG wall-clock
   time for a lower peak memory footprint.

================================================================================
PHASE 8: MONITORING -- PROMETHEUS + GRAFANA
================================================================================

1. STACK (monitoring/docker-compose.yaml): serving-app + Prometheus +
   Grafana.
   docker compose -f monitoring/docker-compose.yaml up -d --build

2. REQUEST LATENCY + COUNT:
   `prometheus-fastapi-instrumentator` -- one line
   (`Instrumentator().instrument(app).expose(app)`) adds a /metrics
   endpoint with request-count and latency-histogram metrics for every
   route.

3. PREDICTION DRIFT:
   - CONCEPT: this is a forecast-serving API, not a live feature-scoring
     one, so there's no incoming raw feature vector to compare against a
     training distribution directly. The analogue used here: a rolling
     window of the last 200 served predictions compared via a
     two-sample KOLMOGOROV-SMIRNOV TEST against the full historical
     training sales distribution.
   - What KS measures: the largest gap between the two samples'
     empirical CDFs. Statistic near 0 = distributions look alike; near
     1 = very different.
   - Why this matters without ground truth: forecast accuracy can't be
     checked until real future sales arrive (could be weeks). Drift is
     a leading indicator checkable immediately.
   - Known limitation: the reference distribution is POOLED across all
     100 series, not per-series.
   - Grafana dashboard GOTCHA: a `$datasource` template variable with no
     default value never resolves -- every panel silently queries a
     literal unresolved string and shows nothing. Fix: omit `datasource`
     on each panel and let Grafana use its single default.

================================================================================
KEY CONCEPTS GLOSSARY (WORTH KNOWING COLD FOR AN INTERVIEW)
================================================================================

- MAPE has 3 framings, each telling a different story: MEAN per-series
  (sensitive to outliers), MEDIAN per-series (robust to outliers),
  AGGREGATE (sum actuals/forecasts across series first, then one MAPE --
  most stable, used here for model selection).
- Global vs. per-series models: per-series = each series' own history
  only; global = one model, all series stacked, entity IDs as features.
- lag_28 over lag_7: use the LARGEST lag that stays valid across the
  ENTIRE forecast horizon, to avoid leaking future information.
- MLflow tracking SERVER vs. bare sqlite file: a server is required the
  moment more than one machine/container needs to resolve model
  artifacts.
- Model Registry ALIASES (e.g. `champion`) vs. deprecated "stages":
  aliases are the modern way to say "this specific version currently
  means X."
- Nested parallelism: an outer parallelism setting (joblib n_jobs) does
  not bound INNER parallelism (BLAS/OpenMP threads each worker spawns)
  unless explicitly pinned via *_NUM_THREADS env vars.
- Prometheus vs. Grafana: Prometheus COLLECTS + STORES time-series
  metrics; Grafana VISUALIZES whatever Prometheus (or another
  data source) has stored.
- Drift monitoring vs. accuracy evaluation: accuracy needs ground truth
  (checked once, offline, in MLflow); drift is a live, leading proxy
  checkable without waiting for ground truth to arrive.
