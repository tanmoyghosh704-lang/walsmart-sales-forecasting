================================================================================
PROJECT ROADMAP & RESOURCE BREAKDOWN: WALMART M5 DEMAND FORECASTING MLOPS
================================================================================

PROJECT OVERVIEW:
An end-to-end, production-shaped demand forecasting system built on Kaggle's
M5 Forecasting - Accuracy dataset (Walmart). Benchmarks 7 forecasting
approaches (naive seasonal baseline, Prophet, SARIMA, Linear Regression,
Random Forest, XGBoost, LightGBM) on 100 high-volume store-item series over a
28-day held-out horizon, tracks and registers every model via MLflow with
conditional champion auto-promotion, versions data via DVC/DagsHub, serves
forecasts via FastAPI + Docker, orchestrates retraining via Airflow, monitors
the live service via Prometheus/Grafana (including a prediction-drift check),
and provides an interactive Streamlit comparison UI. The forecasting models
themselves are deliberately simple -- the pipeline around them is the point.

PHASE 1: DATA ACQUISITION & SCOPING
================================================================================

1. DOWNLOAD RAW M5 DATA:
   kaggle competitions download -c m5-forecasting-accuracy -p data/raw
   cd data/raw && unzip m5-forecasting-accuracy.zip && rm *.zip

   Files: sales_train_validation.csv (30,490 series x 1,913 days),
   calendar.csv (date/holiday/SNAP mapping), sell_prices.csv (weekly
   price per store-item), sales_train_evaluation.csv, sample_submission.csv.

2. SCOPE THE DATASET DOWN (src/data_prep.py):
   - Full dataset has ~30,490 store-item series -- too many to iterate on.
   - Select TOP 100 SERIES BY TOTAL HISTORICAL VOLUME, not a random
     sample. High-volume series have proportionally fewer zero-sales
     days, which matters directly for MAPE (division by near-zero
     actuals otherwise dominates the metric with noise).
   - Side effect worth knowing: volume-based selection skews the subset
     toward FOODS (97/100 series here) -- grocery items are bought far
     more often than e.g. household goods. Not representative of the
     full catalog; a deliberate, stated bias.
   - Reshape wide format (d_1...d_1913 columns) to LONG FORMAT
     (id, date, sales, ...) via pandas.melt -- required by
     Prophet (ds/y columns) and every downstream groupby.
   - Output: data/processed/subset_long.csv (191,300 rows).

3. NAIVE BASELINE, BEFORE ANY MODELING (src/baseline.py):
   - Seasonal-naive (lag-7): each series' last 7 observed training days,
     tiled across the 28-day test horizon. The free lunch any real model
     has to beat to justify its complexity.
   - 28-day held-out test window (matches M5's own competition horizon).
   - MAPE computed multiple ways (see Phase 4, concept: MAPE framings).
   - Result: 78.58% mean per-series MAPE / 10.75% aggregate MAPE.

PHASE 2: EXPLORATORY DATA ANALYSIS
================================================================================

1. NOTEBOOK: notebooks/eda.ipynb
   - Weekly seasonality: weekend sales (~40 units/day) vs. midweek (~28).
   - SNAP (food-assistance) effect: real, consistent bump on SNAP days in

================================================================================
PHASE 3: PER-SERIES MODELS -- PROPHET & ARIMA
================================================================================

1. WHY PER-SERIES FOR THESE TWO:
   Prophet and ARIMA both model a single series' own trend/seasonality/
   autocorrelation structure -- neither has a natural "global across
   series" form. 100 series = 100 independent models for each.

2. PROPHET (src/train.py):
   - One Prophet model per series (additive model: trend + weekly/yearly
     seasonality + holidays + regressors).
   - Holidays fed via Prophet's native `holidays` parameter
     (calendar.csv's event_name_1/date).
   - SNAP fed as `model.add_regressor("snap")` -- a real signal EDA
     found, and its future values are a published schedule, not
     something that needs forecasting.
   - Result: 68.58% mean per-series MAPE / 6.57% aggregate MAPE.

3. ARIMA / SARIMA (src/train_arima.py):
   - `pmdarima.auto_arima`, seasonal=True, m=7 (weekly seasonality),
     snap as an exogenous regressor (X=), same reasoning as Prophet.
   - PARALLELIZED across CPU cores via joblib (a single auto_arima call
     takes ~35s; 100 sequential would be 1hr+).
   - GOTCHA (nested parallelism): joblib's `n_jobs` only bounds worker
     *process* count, not each process's internal BLAS/OpenMP *thread*
     count. numpy/scipy/statsmodels each try to use every core by
     default regardless of how many sibling processes are already
     running. Fix: set OMP_NUM_THREADS, OPENBLAS_NUM_THREADS,
     MKL_NUM_THREADS, NUMEXPR_NUM_THREADS, VECLIB_MAXIMUM_THREADS = "1"
     BEFORE importing numpy/scipy/statsmodels (they read these at
     import time). Without this, "n_jobs=4" can silently use 12+ cores.
   - Result: 85.21% mean / 43.87% median / 18.46% aggregate MAPE --
     WORSE than the naive baseline on every framing. Investigated rather
     than hidden (see Phase 4, concept: MAPE outlier sensitivity).

================================================================================
PHASE 4: GLOBAL ML MODELS -- FEATURE ENGINEERING & TRAINING
================================================================================

1. GLOBAL VS. PER-SERIES (key design fork):
   - Per-series (Prophet/ARIMA): 100 separate models, each blind to every
     other series.
   - GLOBAL (this phase): ONE model per algorithm, trained on all 100
     series stacked into a single table, with store_id/item_id/dept_id/
     cat_id/state_id as FEATURES. Lets the model learn cross-series
     patterns a per-series model structurally cannot see. This mirrors
     how the real M5 competition's top solutions actually approached it.

2. LEAKAGE-SAFE FEATURE ENGINEERING (src/feature_engineering.py):
   - CONCEPT -- why lag_28, not lag_7: this is a 28-day-AHEAD forecast,
     not 1-day-ahead. A lag_7 feature is invalid for most of the test
     window (predicting day 15 of the horizon with "sales 7 days ago"
     needs sales from day 8 of the horizon, which hasn't happened yet).
     lag_28 is the LARGEST lag that stays valid for the ENTIRE 28-day
     horizon (lag_28 on the last test day still points at the last
     training day). Every history feature is built on top of this lag.
   - Features: lag_28, rolling_mean_7_lag28, rolling_mean_28_lag28,
     rolling_std_28_lag28, wday/month/year, is_weekend, has_event, snap,
     sell_price (joined from sell_prices.csv on store_id/item_id/
     wm_yr_wk -- never used by the Prophet/ARIMA phase).
   - Categorical encoding: label/integer codes for tree models (fine --
     trees split on thresholds regardless of encoding); ONE-HOT for
     Linear Regression via sklearn ColumnTransformer (ordinal codes
     would wrongly imply an order a linear model would try to use).
   - Output: data/processed/ml_features.csv (185,800 rows -- 5,500
     dropped per series for insufficient lag_28 history at series start).

3. TRAINING (src/train_ml_models.py):
   - Linear Regression, Random Forest, XGBoost, LightGBM -- one
     `.fit()`/`.predict()` call each (no per-series loop).
   - LightGBM given TRUE categorical columns (pandas `category` dtype +
     `categorical_feature=`) for better split quality than raw integer
     codes.
   - No hyperparameter tuning -- sensible defaults only; the comparison
     and pipeline are the point, not squeezing out the last % of MAPE.
   - Results (aggregate MAPE): LightGBM 5.82%, Linear Regression 6.45%,
     XGBoost 6.48%, Random Forest 7.29%.

PHASE 5: EXPERIMENT TRACKING, MODEL REGISTRY & DATA VERSIONING
================================================================================

1. MLFLOW TRACKING SERVER (not a raw sqlite:/// path):
   mlflow server --backend-store-uri sqlite:///mlflow.db --host 0.0.0.0 \
     --allowed-hosts "host.docker.internal:5000,127.0.0.1:5000,localhost:5000"

   - CONCEPT -- why a server, not a bare local file store: MLflow's local
     file-based artifact store bakes an ABSOLUTE HOST FILESYSTEM PATH
     into each experiment's artifact location at creation time. Works
     fine same-machine, but breaks the moment a client (e.g. a Docker
     container) runs anywhere else -- the path doesn't exist there.
     Routing through a tracking server means clients talk to a network
     address; the server resolves storage on its own filesystem. This is
     what makes the setup portable into Docker.
   - `--allowed-hosts` needed because MLflow 3.x has built-in DNS-
     rebinding protection that 403s requests whose Host header isn't on
     an allowlist (must include the exact host:port a container will
     connect with, e.g. host.docker.internal:5000).

2. LOGGING PATTERN:
   - Per-series models (Prophet, ARIMA): one PARENT run per training job
     + one NESTED run per series (mlflow.start_run(nested=True)),
     logging that series' own params/MAPE and registering it under its
     own name (`prophet_<series_id>`, `arima_<series_id>`).
   - Global models: one run each, registered as `sales_<model_name>`.
   - Model flavors used: mlflow.prophet, mlflow.pmdarima (deprecated but
     functional), mlflow.sklearn, mlflow.xgboost, mlflow.lightgbm --
     each knows how to serialize/deserialize that specific library's
     model object.

3. DATA VERSIONING (DVC + DagsHub):
   dvc remote add origin https://dagshub.com/<user>/<repo>.dvc
   dvc remote modify origin --local auth basic
   dvc remote modify origin --local user <username>
   dvc remote modify origin --local password <token>
   dvc add data/raw data/processed
   dvc push -r origin

   - CONCEPT: DVC hashes directory contents, moves the real bytes into a
     content-addressed cache, and commits only a small `.dvc` pointer
     file to git. Git stays small/fast; DVC's remote holds the actual
     data.
   - Credentials go in `.dvc/config.local` (gitignored), never the
     committed `.dvc/config`.
   - GOTCHA: DVC refuses to `add` a directory git already partially
     tracks (e.g. leftover .gitkeep placeholders) -- `git rm --cached`
     them first.
   - REMEMBER: `dvc push` only pushes DATA. It does NOT push your git
     commit history to DagsHub. If DagsHub's Files tab looks empty
     despite successful `dvc push`, you need a SEPARATE git remote and
     `git push dagshub master` -- two different pushes, two different
     purposes.

4. CHAMPION SELECTION & CONDITIONAL AUTO-PROMOTION:
   - src/compare_models.py: assembles every model's summary + per-series
     MAPE files into one table, sorted by AGGREGATE MAPE.
   - CONCEPT -- why aggregate MAPE, not mean per-series MAPE, as the
     SELECTION metric: ARIMA's mean per-series MAPE (85%) was dragged
     above even the naive baseline by ONE series with an 856% error --
     traced to a genuine stockout mid-test-window, invisible in training
     history, that no history-only model could have anticipated (same
     MAPE small-denominator sensitivity as intermittent retail demand
     generally). A selection metric that lets one pathological series
     disqualify an otherwise-good model is a bad selection metric, even
     though that per-series number is still worth reporting for
     transparency.
   - src/promote_champion.py: re-points the MLflow registry's `champion`
     ALIAS (modern replacement for the deprecated "stage" concept) to
     whichever model has the best aggregate MAPE -- but ONLY if it beats
     the CURRENT champion's aggregate MAPE (looked up via
     `client.get_model_version_by_alias(...)` -> run_id -> that run's
     logged metric, not a cached number). A retrain that regresses
     should not silently overwrite a better model already promoted.
   - Restricted to the 4 GLOBAL models only: each has exactly one
     registered name, so one alias can mean "the current best version of
     this name." Prophet/ARIMA are per-series (100 separately-registered
     names each) -- no single name an alias could represent "the
     champion Prophet model."
   - Winner: LightGBM, 5.82% aggregate MAPE (45.8% relative improvement
     over the naive baseline). Registered as `sales_lightgbm@champion`.

PHASE 6: SERVING -- FASTAPI + DOCKER
================================================================================

1. FASTAPI APP (serving/app.py):
   - GET /health -- liveness + forecast-window info.
   - GET /predict?series_id=...&horizon=... -- loads the requested
     series' Prophet model via `mlflow.pyfunc.load_model
     ("models:/prophet_<series_id>/latest")` (registry URI, not a
     pickle file), cached per-process via `functools.lru_cache`.
   - CONCEPT -- forecast window is bounded, not open-ended: models were
     trained through a fixed date; the `snap` regressor they need for
     future dates only has REAL (not fabricated) values as far as
     calendar.csv actually extends. /predict rejects horizons beyond
     that with a clear error instead of guessing.
   - GET /metrics -- Prometheus scrape endpoint (see Phase 8).

2. DOCKERFILE (serving/Dockerfile):
   docker build -f serving/Dockerfile -t m5-forecast-api .
   docker run -p 8000:8000 -e MLFLOW_TRACKING_URI=http://host.docker.internal:5000 \
     m5-forecast-api

   - GOTCHA: do NOT bake mlflow.db/mlruns into the image (see Phase 5's
     "why a tracking server" concept -- baked-in artifact paths break
     inside a container). Pass MLFLOW_TRACKING_URI as an env var instead.
   - `.dockerignore` matters even with targeted COPY lines: Docker sends
     the ENTIRE build context to the daemon before any COPY runs,
     regardless of what's actually used.

PHASE 7: ORCHESTRATION -- AIRFLOW (DOCKER COMPOSE)
================================================================================

1. WHY DOCKER COMPOSE, NOT NATIVE PIP INSTALL:
   Airflow doesn't officially support running natively on Windows (only
   Linux, or Windows via WSL2/Docker).

2. STACK (docker-compose.yaml): Postgres (Airflow's OWN metadata DB, not
   MLflow's) + webserver + scheduler, LocalExecutor (not the official
   compose file's default CeleryExecutor, which adds Redis + a separate
   worker + triggerer -- overkill for "prove the orchestration works").
   docker compose up airflow-init      # one-off: migrate DB, create admin user
   docker compose up -d                # webserver + scheduler

3. TASK DEPENDENCIES INSTALLED IN AN ISOLATED VENV (airflow/Dockerfile):
   - Installing prophet/mlflow/lightgbm/etc. DIRECTLY into Airflow's own
     Python environment (the officially recommended `pip install
     --constraint <airflow-constraints-url>` pattern) FAILED repeatedly --
     mlflow/prophet's dependency requirements collide with versions
     Airflow's constraints file pins exactly (pandas, then cryptography).
   - Fix: `python -m venv /opt/airflow/task_venv`, install everything
     there instead. Nothing installed in an isolated venv can ever break
     Airflow's own packages. The DAG invokes this venv's python directly.
   - Also needed: `apt-get install libgomp1` (GNU OpenMP runtime) --
     LightGBM's compiled extension needs it AT IMPORT TIME, not just at
     pip-install time; the base Debian image doesn't ship it.

4. DAG STRUCTURE (airflow/dags/retrain_dag.py, dag_id=m5_full_retrain):
     retrain_baseline  ---\
     retrain_prophet   ----\
     retrain_arima     -----+--> compare_models --> promote_champion
     build_features -> retrain_ml_models --/

   - `max_active_runs=1`: catchup=False still auto-runs the single most
     recent past interval on DAG activation, which can overlap with a
     manual trigger -- two concurrent runs each spawning parallel ARIMA
     fits is a real resource-exhaustion risk (see below).
   - `execution_timeout` on every task: a hung task (e.g. a DB heartbeat
     failure with no progress) should fail loudly, not block the DAG
     indefinitely.

5. GOTCHA -- RESOURCE CONSTRAINTS ON SMALL DEV MACHINES:
   Running several memory-heavy tasks CONCURRENTLY (Prophet + ARIMA +
   4 ML models fitting at once, which is the architecturally correct
   parallel DAG design) can exceed what a modest host (e.g. ~14GB RAM
   shared across Windows + WSL2 + Docker + a second WSL distro) can
   sustain -- manifesting as the CONTAINER RUNTIME ITSELF becoming
   unresponsive, not a training script error. Diagnosed via: `docker
   stats` for CPU/memory trend, Docker Desktop's own settings file
   (%APPDATA%\Docker\settings-store.json) to check if it's running in
   WSL2-integration mode, `%USERPROFILE%\.wslconfig` for an explicit
   memory override, `Get-CimInstance Win32_ComputerSystem` for total
   host RAM, and `wsl -l -v` to check for other competing WSL distros.
   A real fix beyond tuning any single task: restructure heavy tasks to
   run SEQUENTIALLY instead of in parallel, trading DAG wall-clock time
   for a lower peak memory footprint.

PHASE 8: MONITORING -- PROMETHEUS + GRAFANA
================================================================================

1. STACK (monitoring/docker-compose.yaml): serving-app + Prometheus +
   Grafana.
   docker compose -f monitoring/docker-compose.yaml up -d --build

2. REQUEST LATENCY + COUNT:
   `prometheus-fastapi-instrumentator` -- one line
   (`Instrumentator().instrument(app).expose(app)`) adds a /metrics
   endpoint with request-count and latency-histogram metrics for every
   route, zero custom instrumentation code.

3. PREDICTION DRIFT (the actual differentiator):
   - CONCEPT: this is a forecast-serving API, not a live feature-scoring
     one -- there's no incoming raw feature vector to compare against a
     training distribution the way a textbook drift check would. The
     analogue used here: a rolling window of the last 200 SERVED
     PREDICTIONS (yhat values, no dates attached) compared via a
     two-sample KOLMOGOROV-SMIRNOV TEST against the FULL HISTORICAL
     TRAINING SALES DISTRIBUTION (also just values, no dates -- KS is a
     pure value-distribution comparison, time-independent).
   - What KS actually measures: the largest vertical gap between the two
     samples' empirical CDFs. Statistic near 0 = distributions look
     alike; near 1 = very different. p-value = how likely this much gap
     is by chance if they were really the same distribution.
   - Why this matters without ground truth: you can't check a forecast's
     ACCURACY in production until real future sales arrive (could be
     weeks). Drift is a LEADING indicator checkable immediately --
     doesn't tell you if a specific forecast was right, tells you if the
     model's outputs still resemble what it learned from.
   - Known limitation (stated honestly, not hidden): the reference
     distribution is POOLED across all 100 series. Querying one
     low-volume series repeatedly makes the statistic look "worse" than
     it should -- a production version would want a per-series baseline.
   - Grafana dashboard GOTCHA: a `$datasource` template variable with no
     default `current` value never resolves -- every panel silently
     queries a literal unresolved string and shows nothing. Fix: omit
     `datasource` on each panel and let Grafana use its single default.

================================================================================
KEY CONCEPTS GLOSSARY (WORTH KNOWING COLD FOR AN INTERVIEW)
================================================================================

- MAPE has 3 framings, each telling a different story: MEAN per-series
  (sensitive to outliers), MEDIAN per-series (robust to outliers),
  AGGREGATE (sum actuals/forecasts across series first, then one MAPE --
  most stable, used here for model selection).
- Global vs. per-series models: per-series = each series' own history
  only; global = one model, all series stacked, entity IDs as features.
- lag_28 over lag_7: use the LARGEST lag that stays valid across the
  ENTIRE forecast horizon, to avoid leaking future information.
- MLflow tracking SERVER vs. bare sqlite file: a server is required the
  moment more than one machine/container needs to resolve model
  artifacts.
- Model Registry ALIASES (e.g. `champion`) vs. deprecated "stages":
  aliases are the modern way to say "this specific version currently
  means X."
- Nested parallelism: an outer parallelism setting (joblib n_jobs) does
  not bound INNER parallelism (BLAS/OpenMP threads each worker spawns)
  unless explicitly pinned via *_NUM_THREADS env vars.
- Prometheus vs. Grafana: Prometheus COLLECTS + STORES time-series
  metrics; Grafana VISUALIZES whatever Prometheus (or another
  data source) has stored. Neither does the other's job.
- Drift monitoring vs. accuracy evaluation: accuracy needs ground truth
  (checked once, offline, in MLflow); drift is a live, leading proxy
  checkable without waiting for ground truth to arrive.
